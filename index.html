1. What AI Sees

The Gateway Explained

Modern vehicles don't put every ECU on the OBD-II diagnostic bus (pins 6/14). Instead, a central gateway bridges internal networks (PT-CAN, K-CAN, F-CAN, etc.) and selectively exposes signals to the diagnostic port.

We capture and decode what the gateway chooses to expose — not manufacturer-internal data, but the signals that matter for diagnostics: wheel speeds, steering angle, yaw rate, battery voltage, door status, brake pressure, HVAC, cluster warnings, and more.

Coverage varies by manufacturer, model, and year; we discover it per vehicle.

Signal Categories (Gateway-Exposed)

Identity: VIN, odometer, ECU part numbers/SW versions

Battery: Resting voltage, crank profile (min/recovery), alternator running — 100ms resolution on pin 16

Powertrain: Engine RPM, load, coolant/IAT/ambient temp, throttle position, fuel level, OBD PIDs, UDS 0x22 reads

Transmission: Gear position, TCM data, UDS 0x22 reads

Chassis: 4× wheel speed, steering angle, yaw rate, lateral accel, brake pressure, ABS DTCs

Body/Electrical: Door/lock/belt/light status, HVAC data, cluster warnings, gateway DTCs

OBD Standard: Mode 01/09 PIDs, DTCs (Mode 03/07/0A), Mode 06 monitor results

What This Enables

From gateway-exposed signals we detect and diagnose wheel bearing/hub faults, door latch failures, battery/alternator/wiring issues, ESC false activation, steering sensor drift, and yaw/lateral acceleration sensor zero errors.

Intelligence Layer

We cross-reference DTCs with live signal behaviour, compare left/right and front/rear symmetry, detect sub-threshold anomalies (misfires below DTC threshold, sensor drift before fault codes), and build per-vehicle baselines for trend monitoring and early warning.

4. K-Line Direct ECU Access

K-Line Address Reference (Common Defaults)

Engine ECU: Address: 0x10 | Protocol: ISO 14230-4 (ATSP 4) | Use Case: When gateway blocks UDS

Gateway: Address: 0x19 | Protocol: ISO 14230-4 (ATSP 4) | Use Case: Direct gateway diagnostics

ABS: Address: 0x03 | Protocol: ISO 14230-4 | Use Case: Gateway-independent

Cluster: Address: 0x17 | Protocol: ISO 14230-4 | Use Case: Mileage/identity verification

Transmission: Address: 0x02 | Protocol: ISO 14230-4 | Use Case: TCM direct

HVAC: Address: 0x08 | Protocol: ISO 14230-4 | Use Case: Body diagnostics

K-Line Notes

Vehicle-dependent: K-Line must be wired to pin 7 on target ECU. Not all manufacturers/vehicles support all addresses. Common on VW Group, BMW, and many European platforms.

Arbitrary addressing: Any 8-bit K-Line address (0x00–0xFF) reachable via ATSH — the table above shows common defaults only.

ISO 9141-2 support: 5 baud init (ATSI/ATSP 3) for older Asian, European, Chrysler ECUs that predate KWP2000.

Custom K-Line timing: STIFI (custom fast init), STITW (per-timing-parameter config), STIIAP (init address parity), STIP/STIP1X (communication parity & P1 max) — enables access to ECUs violating ISO timing specs.

Gateway-Blocked ECUs: K-Line ISO-TP direct to Engine (0x10) and Gateway (0x19) when CAN gateway blocks UDS — no bench removal required.

5. Hardware & Capture Platform

OBDLink EX — Technical Specifications (OBD-II Port Only)

Interface: USB 2.0 (SLCAN), Bluetooth 2.0 SPP, WiFi TCP (port 35000)

Primary Capture: SLCAN binary BLF @ full bus speed (no ATMA text bottleneck)

UART Baud: Up to 921600 (STBR) — 10× default, eliminates USB bottleneck

CAN (HS-CAN): ISO 15765-4 (11/29-bit, 500/250 kbps), ISO 11898 raw, CAN FD (OBDLink EX) — pins 6/14

MS-CAN (Medium Speed): ISO 11898 / ISO 15765-4 @ 33.3/100/125 kbps — Ford body/comfort modules via OBD-II pins 3/11 (STP 61–64)

SW-CAN / GMLAN: SAE J2411 (Single Wire CAN) @ 33.3 kbps — GM body/engine comms via OBD-II pin 1 (STP 61–64, STCSWM modes 2,5)

K-Line: ISO 9141-2 (5 baud init), ISO 14230-4 KWP2000 (5 baud init, fast init, custom via STIFI/STITW) — ISO-TP direct ECU access (pin 7, vehicle-dependent)

J1850: Not supported on OBDLink EX (STN2120) — supported on MX/LX/MX+/CX family

J1939: 29-bit, 250 kbps — PGN filtering (STFPGA), multi-PGN monitor, TP.CM/TP.DT reassembly, DM1/DM2

Hardware Filtering: 2× 32-bit acceptance code/mask filters (pre-buffer, zero saturation)

Software Filtering: Pass filters, block filters, flow control filters (ISO-TP vs raw CAN separation)

Filter Stack: CAN hardware → flow control → pass/block → output

Voltage Telemetry: Factory-calibrated 12-bit ADC (1:7.2 divider, 0–24V range, ±0.2V accuracy, configurable polling 10ms–10s) — Pin 16 only

Addressing Formats: Normal (STCAF 0), Extended (STCAF 1), Mixed (STCAF 2), Normal Fixed (STCAF 3) + ISO 15765-4 presets (STP 33–42)

Periodic TX: Configurable intervals via STPPMA/STPPMD/STPPMC — live monitoring of diagnostic-bus signals during adaptations

Arbitrary Transmit: STPX — up to 2KB frames, any protocol, custom header/data/length/timeout/response count/flags

ISO-TP: Multi-frame reassembly, flow control auto (STCAF, STCFCPA 11-bit, STFFCA 29-bit for custom FC IDs)

Custom CAN Timing: STCTR — register-level timing configuration for non-standard CAN buses

PowerSave: Software-configurable sleep/wake (UART inactivity, voltage level/change, protocol activity, external pin/USB host detect)

Voltage-Change Wake: Detects crank dip / alternator rise — configurable threshold & sample window (STSLVG, STSLVGW)

Protocol-Activity Sleep/Wake: Sleep on bus silence, wake on CAN/K-Line activity (STSLPA, STSLPAW, STSLPAS) — unattended logging capable

Silent CAN Monitoring: STCMM 0 (default) — zero bus load, never disturbs safety-critical systems

Active CAN Node: STCMM 1 — transmits ACKs, participates on bus (required for PGN requests)

GPIO: 4× configurable I/O (direction, read, write, open-drain, pull-up/down)

Firmware: Field-upgradable via USB

Message Buffer: 2KB (4KB on MX+) — burst capture without BUFFER_FULL

Software Stack

python-can (4.6.1) SLCAN interface, frame I/O, isotp stack

cantools (44.1.0) DBC parsing, real-time decode, BLF/ASC/CSV export

obdlink_ex_ref (Custom) OBDLink EX command reference, voltage conversion, CAN ID helpers, session checklist

Capture Workflow

  1. Pre-capture: Hardware filters configured (ATCF → ATCM/STCM) to exclude known noise on diagnostic bus
  2. Capture: SLCAN binary BLF with microsecond-epoch timestamps
  3. Correlation: Operator actions timestamped → post-process matched to CAN frames
  4. Decode: Real-time or post-capture via cantools + gateway-exposed DBC signals

6. Advanced Capabilities

6.1 Security Access (UDS 0x27)

Security-access operations (ECU replacement, immobilizer sync, variant coding, adaptation writes) with written authorisation only. Platform-specific — requires verified seed/key algorithm. Not a universal unlock.

6.2 Gateway Wake Strategies

  • K-Line 0x10/0x19 with 5 baud init or fast init
  • Custom fast init (STIFI) for difficult ECUs
  • USB host detect sleep/wake (EX rev 2.5+)

6.3 J1939 (Commercial Vehicles)

  • PGN filtering (STFPGA) — multi-PGN simultaneous monitor
  • Target address filtering (specific ECU, broadcast FF, or all)
  • TP.CM / TP.DT multi-frame reassembly (BAM + RTS/CTS)
  • J1939-73 diagnostics (DM1/DM2 faults)
  • ACK frame processing
  • ATJ S/ATJ E — little-endian PGN request control

6.4 CAN FD & Addressing

  • CAN FD capture (OBDLink EX) — DLC up to 64 bytes on diagnostic bus
  • Addressing formats: Normal, Extended, Mixed, Normal Fixed (STCAF 0–3)
  • ISO 15765-4 preset formats (STP 33–42) — pre-configured for OEM variants
  • Custom flow control ID pairs (STCFCPA 11-bit, STFFCA 29-bit)
  • Extended addressing: STCAF 1,xx + ATTA yy (gateway-separated ECUs)
  • Mixed addressing: STCAF 2,xx (same extended addr for Tx/Rx)

6.5 Periodic Transmission & Arbitrary Transmit

  • STPPMA interval, header, data — add periodic message (returns handle)
  • STPPMD handle — delete specific periodic message
  • STPPMC — clear all periodic messages
  • STPX — arbitrary frame transmit: custom header, data (or length + DATA> prompt), timeout, response count, extended address, flags — up to 2KB, any protocol
  • Use cases: ECU simulation, actuator testing, custom service routines, parameter writes (with authorisation)

6.6 Non-Standard & Custom Protocols

  • Custom CAN protocol: STCSP — user-defined CAN parameters
  • Custom CAN baud: STCBR / STCBA — non-standard bit rates
  • Register-level timing: STCTR — direct CAN timing register access
  • ISO 15765-4 presets: STP 33–42 — pre-configured addressing format variants
  • Adaptive timing: ATAT 1 (normal) / ATAT 2 (aggressive) — auto-tunes inter-frame timeout per vehicle

7. Vehicle Coverage — Access Methodology

We do not maintain a "supported vehicle list." Our access model:

OBD-II Diagnostic CAN (pins 6/14): Scope: All vehicles 1996+ (legislated) | Dependency: Gateway exposes signals — varies by manufacturer/model/year

K-Line ISO-TP (pin 7): Scope: Engine, Gateway, ABS, Cluster, TCM, HVAC, others | Dependency: Physical wiring to pin 7 by manufacturer — common VW Group, BMW, many European

MS-CAN (Ford, pins 3/11): Scope: Body/comfort modules (BCM, HCM, etc.) | Dependency: Ford vehicles with MS-CAN on OBD port — verified hardware capability

SW-CAN / GMLAN (GM, pin 1): Scope: Body/engine comms | Dependency: GM vehicles with SW-CAN on OBD port — verified hardware capability

J1939 (pins 6/14, 250 kbps): Scope: Commercial vehicles (truck, bus, agriculture) | Dependency: SAE J1939 implementation — PGN-based

ISO 9141-2 (K-Line, 5 baud): Scope: Pre-2000s Asian/Euro/Chrysler | Dependency: Legacy protocol support via same K-Line hardware

Gateway-exposed signals: Discovered per vehicle. No manufacturer excluded a priori. DBC libraries built per platform from real captures.

Explicit non-access: Internal buses (PT-CAN, K-CAN, F-CAN, EV-CAN, C-CAN, proprietary) require physical taps behind gateway — not available via OBD-II port.
